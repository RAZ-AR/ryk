# Native App Plan — Expo / React Native + вход Google · Apple · Email

> План перехода к нативному клиенту в App Store. Решение и его цена — в
> [ADR-012](18-decisions-adr.md). Здесь — порядок работ.
>
> ⚠️ **Предупреждение, записанное честно:** [ADR-001](18-decisions-adr.md)
> откладывал нативное до подтверждённого retention, и критерии пилота
> ([10-mvp-scope](10-mvp-scope.md)) ещё не набраны. Решение идти в App Store
> раньше — осознанное, принято владельцем продукта. План написан так, чтобы
> ни один шаг не пропал впустую, даже если пилот не подтвердит гипотезу:
> вынос API и мульти-вход полезны и вебу.

## Что уже готово, а что предстоит

Проверено по коду, не по памяти:

| Слой | Файлов | Судьба |
|---|---|---|
| Движки `lib/engine/*` | 11 | ✅ переезжают как есть, чистый TS без React |
| AI-слой, i18n-логика, аналитика | — | ✅ переезжают |
| Схема БД, Prisma, Supabase | — | ✅ остаётся, меняется только модель пользователя |
| Server actions `app/actions/*` | 13 | ❌ становятся HTTP API |
| UI, CSS Modules, дизайн-система | ~40 | ❌ пишутся заново на RN |
| Вход по `initData` | — | ➕ дополняется тремя провайдерами |
| Пуши через Telegram | — | ➕ дополняются APNs/FCM |

**Mini App не выключаем.** Приглашения и «свидетель» живут в мессенджере, где
люди уже переписываются, — это преимущество, а не наследие. Сервер после
выноса API обслуживает оба клиента.

## Фаза N1 — Монорепо и общее ядро

Сейчас всё лежит в корне одного Next.js-приложения. Двум клиентам нужен общий
код без копипасты.

```
ryk/
├── apps/
│   ├── web/        ← нынешний Next.js: Mini App + API
│   └── mobile/     ← Expo
├── packages/
│   ├── core/       ← lib/engine/*, типы, zod-схемы, i18n-словари
│   └── tokens/     ← значения дизайн-токенов в TS (общие для CSS и RN)
└── prisma/
```

- pnpm workspaces (пакетный менеджер уже pnpm@11).
- `packages/core` не знает ни про React, ни про Next — только TypeScript и Prisma-типы.
- Токены переезжают из `app/tokens.css` в TS-объект, а CSS-переменные **генерируются** из него. Иначе палитра разъедется между вебом и приложением, а правило «hex живёт только в одном месте» ([17-design-system](17-design-system.md)) держится ровно до первой копипасты.

**Гейт:** веб собирается и проходит тесты из новой структуры; ни одного дублированного модуля движка.

## Фаза N2 — API вместо server actions

13 файлов `app/actions/*` — это протокол Next.js между сервером и его же
React-деревом. Нативный клиент их вызвать не может.

**Развилка (нужно решение):**

| | tRPC | Route Handlers + zod |
|---|---|---|
| Типы клиент↔сервер | выводятся сами | пишутся руками или генерируются |
| Новых зависимостей | tRPC + сервер-адаптер | только zod |
| Сторонние потребители API | неудобно | обычный REST |
| Связанность | клиент привязан к типам сервера | слабая |

**Рекомендация — tRPC:** оба конца на TypeScript в одном репозитории, и типы
экшенов уже описаны (`ScheduleResult`, `AddResult` и прочие) — они станут
контрактом без переписывания. Если позже понадобится публичный API, поверх
tRPC можно выставить REST-фасад.

Порядок: каждое действие переезжает вместе со своим тестом, веб переключается
на вызов API, `"use server"` удаляется. Экшены переезжают по одному, а не все
разом — иначе неделю нельзя будет проверить ни одним запуском.

**Гейт:** веб работает полностью через API; все 183 теста зелёные; ни одного `"use server"` в `app/actions`.

## Фаза N3 — Аккаунты: Google · Apple · Email

Самая большая часть, и она же меняет данные.

### Что не так с нынешней моделью

`User.telegramId String @unique` — обязательное поле. Пользователь **есть**
Telegram-аккаунт. Для четырёх способов входа нужна отдельная сущность:

```prisma
model Account {
  id                String   @id @default(uuid())
  userId            String
  provider          AuthProvider     // TELEGRAM | GOOGLE | APPLE | EMAIL
  providerAccountId String           // sub из id_token, telegramId, e-mail
  email             String?
  createdAt         DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([provider, providerAccountId])
  @@index([userId])
}
```

Миграция: `telegramId` становится nullable, существующие значения переезжают в
`Account` как `TELEGRAM`. Данные пилотных пользователей при этом не теряются —
это перенос, а не пересоздание.

### Развилка (нужно решение): чем делать вход

| | Supabase Auth | Свой OAuth на `jose` |
|---|---|---|
| Google, Apple, Email OTP | из коробки | пишем сами |
| **Apple client secret** | ротирует сам | JWT, который **истекает и требует ротации** — своя инфраструктура |
| **Отправка почты для OTP** | входит | нужен отдельный провайдер (Resend/Postmark) и домен с DKIM |
| Наш `jose`-JWT и сессии | придётся связать две системы | остаётся как есть |
| Контроль | ниже | полный |

**Рекомендация — Supabase Auth.** Supabase уже в стеке как Postgres
([ADR-003](18-decisions-adr.md)), а два пункта из таблицы — ротация клиентского
секрета Apple и доставка почты — это инфраструктурные задачи, не имеющие
отношения к продукту. Связывание делается один раз: Supabase выдаёт
подтверждённую личность, мы по ней находим или заводим `Account` и выпускаем
**свой** сессионный токен. Тогда вся остальная система, включая Telegram-вход,
не меняется вовсе.

### Токены на мобильном

В приложении нет httpOnly-cookie, на которой держится веб. Нужны:

- короткоживущий access-JWT (наш, `jose` уже есть) + refresh-токен;
- хранение в `expo-secure-store` (Keychain), **не** в AsyncStorage;
- ротация refresh при каждом обновлении, инвалидация при удалении аккаунта.

### Требования Apple, которые касаются входа

- **Sign in with Apple обязателен**, если есть Google — а он у нас будет. Хорошо, что Apple и так в списке.
- Удаление аккаунта прямо в приложении — **уже есть** (`deleteAccount`, [PRD §8](04-product-prd.md)).
- Экспорт данных — **уже есть** ([profile/export](../app/api/profile/export/route.ts)).
- Правила Apple меняются: перед подачей свериться с актуальным App Review Guidelines, а не с этим документом.

**Гейт:** на вебе и в приложении вход всеми четырьмя способами; вход двумя разными способами в один аккаунт связывается, а не плодит дубли; удаление аккаунта чистит все `Account`.

## Фаза N4 — Клиент на Expo

Порядок экранов — по недельному циклу, а не по «сначала все списки»:
`Сейчас` → недельный цикл → чек-ин → `Хочу` → `Было` → онбординг → профиль.
После первых трёх приложение уже проверяет главную гипотезу.

**Чем заменяется вёрстка:**

| Веб | Expo |
|---|---|
| CSS Modules | StyleSheet поверх `packages/tokens` |
| `mask-image` вырубки билета | `react-native-svg` — билет рисуется силуэтом целиком |
| `backdrop-filter` дока | `expo-blur` |
| `next/font` (Prata, PT Serif, Plex Mono, Caveat) | `expo-font`, те же файлы |
| `prefers-reduced-motion` | `AccessibilityInfo.isReduceMotionEnabled` |

Анимации (компостер, отрыв корешка) — `react-native-reanimated`. Их немного и
они смысловые: у продукта Motion = 2 ([§1](17-design-system.md)), так что
переносится ровно то, что есть, без добавления «нативной живости».

**Гейт:** цикл `выбрал → подтвердил → чек-ин → воспоминание` проходится на устройстве.

## Фаза N5 — Пуши и приглашения без Telegram

- `expo-notifications` + APNs; серверные нуджи ([lib/engine/nudges.ts](../lib/engine/nudges.ts)) получают второй канал доставки рядом с телеграмным — движок расчёта не трогаем, меняется только транспорт.
- Приглашения: universal links + системный share sheet вместо телеграм-ссылки.
- **Честно про потерю:** «свидетель» в Telegram работает, потому что человек и так там переписывается. Через push к незнакомому приложению это слабее — метрику принятых приглашений после релиза надо смотреть отдельно.

## Фаза N6 — Публикация

- Apple Developer Program — **$99/год**, оформляется тобой.
- EAS Build (сборка в облаке, свободный тариф) → TestFlight → App Review.
- Политика конфиденциальности по публичному URL, App Privacy details, возрастной рейтинг, скриншоты, иконка.
- **Главный риск ревью — 4.2 Minimum Functionality.** Против него работает то, что приложение делает вещи, невозможные в вебе: локальные пуши-нуджи, календарь, камера для фото воспоминания. Это не «фичи для галочки» — они уже есть в продукте, их надо просто использовать нативно.

## Риски

| Риск | Что делаем |
|---|---|
| **Два клиента — двойная поддержка.** Каждая правка UI делается дважды | Держим общими токены, копию и движки. Расхождение допускаем только там, где платформа этого требует |
| **Гипотеза не подтвердится, а денег потрачено больше** | Фазы N1–N3 полезны вебу сами по себе. Если пилот провалится, выброшенной окажется только N4 |
| **App Review отклонит** | Готовим нативные возможности до подачи, а не после отказа |
| Apple client secret истекает | Снимается выбором Supabase Auth |
| Расхождение палитры между вебом и приложением | CSS-переменные генерируются из общих токенов, а не пишутся руками |

## Порядок

`N1 → N2 → N3` — фундамент, полезен вебу независимо от исхода.
`N4 → N5 → N6` — собственно приложение.

N3 можно делать параллельно с N2: они трогают разные файлы.
