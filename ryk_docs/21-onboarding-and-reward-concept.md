# Онбординг и награда за прожитую историю

> Концепт, не спецификация. Два вопроса: **как знакомиться** и **что человек получает,
> когда событие состоялось**. По каждому — два альтернативных решения и рекомендация.
> Код по этому документу пишется отдельной задачей.

## Задача

1. **Онбординг.** Сейчас это анкета. Нужен ритм «одна мысль — один экран» и сквозная
   метафора, чтобы знакомство ощущалось как настройка вещи, а не как заполнение профиля.
2. **Награда.** Событие состоялось — и что? Сейчас: ничего. Нужен момент и след.

## Диагноз текущего состояния

**Онбординг** (`components/onboarding/OnboardingFlow.tsx`, 7 шагов): welcome → категории
(сетка 3×3) → свайп 12 проб → «хороший момент» (textarea) → «что откладывается»
(textarea) → барьеры + окна (чипы) → параметры (чипы + город).

Три проблемы:

- **Ничего не накапливается.** Каждый экран самодостаточен и уходит бесследно. Прогресс
  показан служебной плашкой «раздел 03» — это счётчик, а не объект.
- **Четыре экрана подряд — поля ввода.** После свайпа (лучший экран флоу, там живёт
  билет) идут два textarea и два набора чипов. Темп падает ровно там, где человек уже
  вложился и его проще всего потерять.
- **Финал ничего не выдаёт.** Кнопка «Готово» → `router.refresh()` → лента. Apple-ность
  setup-флоу не в скруглениях, а в том, что в конце ты получаешь **предмет**: часы
  показывают циферблат, AirPods — анимацию кейса. Здесь предмета нет.

**Завершение** (`components/week/CheckinView.tsx`): «Сделано» → эмоция чипом → фраза →
`completeStory()` → refresh. Самая дорогая вещь в продукте — состоявшееся событие, наш
North Star — оплачивается сменой экрана. `FilmFrame` в архиве появляется молча.

Одной строкой: **онбординг ничего не выдаёт, а завершение ничего не оставляет.**

## Часть I. Онбординг

### Решение A: «Касса» — билет выписывается на глазах

**Концепция.** Сверху экрана лежит бланк билета, пустой. Каждый ответ вписывает в него
строку. К последнему экрану бланк заполнен целиком, кроме одной строки — её дописывает
Ryk. Билет отрывается по перфорации и становится первой неделей.

**Ключевой ход — вопросы переписаны как поля билета**, а не как поля профиля:

| Было (профиль) | Стало (строка билета) |
|---|---|
| «Твой город» | **МЕСТО** |
| «Когда ты свободен» | **ВРЕМЯ** |
| «Комфортный бюджет» | **ЦЕНА** |
| «С кем ты обычно» | **КТО** |
| категории + свайп проб | **РОД** |
| — | **ЧТО** ← вписывает Ryk |

Это не косметика. Это снимает коллизию с принципом 4 дизайн-системы
(«билет — только для впечатления, не для служебных блоков»): билет здесь не декорация
поверх формы — он **действительно билет на первое впечатление**, и человек своими
ответами его выписывает. Служебной формы на экране не остаётся вовсе.

**Прогресс — это заполненность бланка, а не «шаг 3 из 7».** Пустые строки — пунктир,
заполненные — ink, текущая — розовая (один розовый акцент на экран, принцип 1).
Служебная плашка со счётчиком шагов убирается.

**Два textarea переезжают на оборот.** «Хороший момент» и «что откладывается» — самые
ценные для движка ответы, но в строку бланка они не лезут. После того как лицевая
сторона заполнена, билет переворачивается: *«На обороте — две строки, которые видит
только Ryk»*. Обратная сторона — это причина, по которой здесь вообще есть свободный
текст, а не ещё один набор чипов.

**Финал.** Ryk дописывает строку **ЧТО** (первая история недели, подобранная по
ответам) → билет отрывается по перфорации → корешок остаётся в руке → это уже
рабочий экран недели. Setup закончился выдачей предмета.

**Wireframe (375px):**

```
┌──────────────────────────────┐
│                              │
│ ┌──────────────────────────┐ │ ← бланк, ~104px, липкий сверху
│ │ RYK · БИЛЕТ ○ ○ ○        │ │   заполненное — ink
│ │ МЕСТО   Белград          │ │   пустое — пунктир
│ │ ВРЕМЯ   ─────────        │ │ ← текущая строка розовая
│ │ ЦЕНА    ─────────        │ │
│ └──────────────────────────┘ │
│                              │
│  Когда у тебя случается      │ ← вопрос, PT Serif 28/1.2
│  свободное время?            │
│                              │
│  [ будни утром  ]            │ ← чипы, крупные
│  [ будни вечером ]           │
│  [ суббота днём ]            │
│  [ выходные вечером ]        │
│                              │
│                              │
│ ──────────────────────────── │
│ [        Дальше          ]   │ ← фикс. низ, safe-area
└──────────────────────────────┘
```

**Трудозатраты:** средние. Новый компонент `TicketBlank` (бланк + анимация вписывания
строки), переразметка семи экранов, финальная сцена отрыва. Логика `completeOnboarding`
и данные не меняются — меняется только порядок вопросов и подача.

### Решение B: «Окошко» — разговор, билет печатается в финале

**Концепция.** Никакого бланка во время вопросов. Экран почти пуст: один вопрос крупной
серифой по центру, ответ под ним, «Дальше» внизу. Ответы уходят вверх узкой лентой
моноширинных строк — как чек, выползающий из кассового аппарата. В финале лента
сворачивается и **печатается** в билет одним движением.

**Отличие от A по существу:** A даёт непрерывную обратную связь (видно, как копится),
B копит напряжение и тратит его на один сильный финал.

**Wireframe:**

```
┌──────────────────────────────┐
│ БЕЛГРАД · БУДНИ ВЕЧЕРОМ      │ ← лента ответов, 11px моно, ink/40
│                              │
│                              │
│      Сколько ты готов        │
│      потратить на            │
│      хорошую историю?        │
│                              │
│      [ до 1500 ]             │
│      [ до 4000 ]             │
│      [ не важно ]            │
│                              │
│                              │
│ ──────────────────────────── │
│ [        Дальше          ]   │
└──────────────────────────────┘
```

**Трудозатраты:** низкие. Почти вся работа — типографика и вёрстка; новых компонентов
один (лента).

**Риск:** прогресс невидим. Человек не знает, сколько ещё, и на седьмом вопросе это
читается как бесконечность. Плюс финал в B — единственная награда за весь флоу: не
зайдёт анимация — не зайдёт ничего.

### Рекомендация: A

B честнее по трудозатратам и ближе к «чистому Apple 2026» — но у Ryk уже есть свой
предмет, и терять шесть экранов, в течение которых он мог бы собираться, жалко.
Непрерывное «видно, как копится» решает главную беду текущего флоу (ничего не
накапливается) прямо, а не обещанием финала.

Тренд подтверждается и снаружи: one-question-per-screen с **видимым** прогрессом —
основной паттерн онбординга 2026, и видимость прогресса в исследованиях идёт в паре с
дроблением, а не вместо него ([NN/g через UXPin](https://www.uxpin.com/studio/blog/what-is-progressive-disclosure/),
[Lollypop](https://lollypop.design/blog/2025/may/progressive-disclosure/)).

### Экран за экраном (решение A)

| # | Строка бланка | Вопрос | Ввод |
|---|---|---|---|
| 0 | — | Обещание. Логотип, «Одна настоящая история каждую неделю» | «Начать» / «Пропустить» |
| 1 | **МЕСТО** | Где сейчас твоя жизнь? | инпут города (префилл из Telegram) |
| 2 | **РОД** | Что делает неделю живой? | сетка 3×3 категорий |
| 3 | **РОД** | 12 проб | свайп билетами (без изменений — экран работает) |
| 4 | **ВРЕМЯ** | Когда у тебя случается свободное время? | чипы окон |
| 5 | **ЦЕНА** | Сколько стоит хорошая история? | чипы бюджета |
| 6 | **КТО** | С кем ты чаще всего? | чипы social mode |
| 7 | оборот | Расскажи момент, когда тебе было по-настоящему хорошо | textarea |
| 8 | оборот | А что всё откладывается? | textarea + барьер чипом |
| 9 | **ЧТО** | — | Ryk вписывает историю, билет отрывается |

Шаг 9 — единственный экран, где Ryk **пишет сам**, и это должно быть видно: строка
проявляется по буквам, курсором. Порядок изменился намеренно: город и категории ушли
вперёд (дёшево ответить, бланк сразу непустой), свободный текст — назад, когда человек
уже вложился.

Барьер («что мешает») перестаёт быть отдельным экраном и становится чипами под вторым
textarea: это уточнение к «что откладывается», а не самостоятельный вопрос.

**Пропуск сохраняется на каждом шаге.** Пустая строка бланка — нормальный исход, не
упрёк: пунктир остаётся пунктиром, никаких «заполни, чтобы продолжить», кроме города.

### Копия

Вопросы — от Ryk, на «ты», без языка продуктивности (14-brand-and-copy). Проверено на
запрещённые формулировки: чисто.

- Экран 0: **«Жизнь не должна ждать свободного времени.»** / «Начать жить чуть больше»
- Экран 4: **«Когда у тебя случается свободное время?»** (не «выбери удобные слоты»)
- Экран 7: **«Расскажи про момент, когда тебе было по-настоящему хорошо.»**
- Экран 9: **«Билет выписан. Осталось прийти.»**

## Часть II. Награда за состоявшееся событие

### Что не подходит

Очки, уровни, значки, коллекции «5 из 10», серии. Прямо запрещено §10 дизайн-системы и
принципом 7. Награда в Ryk не может быть **счётом** — только **следом**.

### Решение A: «Погашение» — корешок гасится сувениром

**Концепция.** У каждой истории недели есть маленькое задание из физического мира:
привезти камень, сфотографировать билет, взять визитку, сохранить чек. Это не
доказательство и не отчёт — это то, **чем гасится билет**. Верхняя часть билета уходит,
корешок остаётся, и на корешке — то, что ты принёс.

**Задание выдаётся в момент commit, а не после события** — иначе камень уже не найти.
Оно живёт мелкой моношириной прямо на корешке выбранного билета:

```
┌──────────────────────────────┐
│ ▓▓▓▓ фото ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │
│ СБ ─────────────── 19:00     │
│    Органный концерт          │
├ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤
│ ● КУЛЬТУРА          ▌▌│▌│▌▌ │
│ на корешок: программка       │ ← новая строка
└──────────────────────────────┘
```

**Каталог сувениров по категориям** (по одному на историю, выбирается детерминированно
по `weeklyStoryId` — чтобы не менялся при перезагрузке):

| Категория | Сувениры |
|---|---|
| NATURE | камень с места · лист · горсть песка · фото горизонта |
| CULTURE | программка · корешок билета · фото афиши · строчка, которая осталась в голове |
| DISCOVERY | визитка · спичечный коробок · чек · фото двери, в которую вошёл |
| MOVEMENT | фото обуви после · номер участника · трек |
| CONNECTION | его почерк на салфетке · общее фото · фраза, которую он сказал |
| JOY | фото тарелки · этикетка · то, что осталось несъеденным |
| CHALLENGE | фото за секунду до · время на часах · первая мысль после |
| REST | фото окна · книга, которую открыл · время, когда проснулся |
| CONTRIBUTION | имя человека, которому помог · фото рук · записка |

Формат — свободный: **фото или строка**. `Memory.media` и `Memory.note` уже есть.

**Сувенир необязателен, и это не смягчение, а условие.** Корешок гасится и пустым: с
датой, местом и эмоцией. Если сувенир обязателен — это proof-of-work, недоверие к
пользователю и давление в чистом виде. Правило: **неделя засчитана по факту события, а
не по наличию сувенира**, и нигде в интерфейсе нет «ты не привёз».

**Сцена погашения.** Реюзаем то, что уже написано: компостер и отрыв корешка живут в
`components/wishlist/WishSchedule` (v0.8 дизайн-системы) — тот же жест, применённый к
билету.

1. «Сделано» → компостер пробивает билет розовым следом, в просечке проступает дата.
2. Эмоция чипом, одна фраза — как сейчас.
3. Слот следа: **«Что осталось?»** — фото или строка. Кнопка «ничего не осталось»
   равноправна, без серого цвета и без предупреждений.
4. Верхняя часть билета уходит вверх и гаснет. Корешок остаётся один на бумаге.
5. **«Этот момент теперь твой.»** (копия уже есть в 14-brand-and-copy)
6. Корешок падает в архив, к остальным.

Всё под `prefers-reduced-motion`: без движения — просто конечное состояние.

**Трудозатраты:** средние. Каталог заданий (константа + i18n), две колонки в схеме,
экран погашения, отрисовка сувенира на корешке в архиве.

### Решение B: «Конверт недели»

**Концепция.** Сувенир, фото и фраза кладутся в конверт, конверт запечатывается и уходит
в архив закрытым. Открывается по тапу — внутри всё, что было на той неделе.

**Плюс:** тайна и повод возвращаться в архив; конверт вмещает несколько предметов без
переверстки.

**Минус, из-за которого не рекомендую:** вводит второй объект-носитель памяти рядом с
билетом и кадром плёнки — их станет три. И прячет память за лишний тап: архив
превращается в ряд одинаковых закрытых прямоугольников, по которым не пробежаться
глазами. Сейчас архив читается плёнкой, и это лучше.

### Рекомендация: A

Корешок уже существует в компоненте `Ticket` (`stub`), уже несёт мету и штрихкод, и уже
умеет отрываться. Решение A ничего не изобретает — оно **доводит до конца метафору,
которая в системе с самого начала**: билет отдают, корешок остаётся у тебя. Сувенир
даёт корешку содержание, из-за которого его хочется хранить.

Отдельно стоит сказать честно: устоявшегося рыночного паттерна «сувенир вместо серии»
нет — поиск по обзорам механик 2026 даёт очки, значки и лиги, а из не-игровых альтернатив
только ритуалы и identity-based рефрейминг ([StriveCloud](https://www.strivecloud.io/blog/gamification-apps-experience),
[Yu-kai Chou](https://yukaichou.com/lifestyle-gamification/best-gamified-productivity-apps/)).
Это одновременно риск (не на что опереться) и повод — механика, которой ни у кого нет,
и при этом ровно в характере продукта.

### Аудит на тёмные паттерны

| Проверка | Статус |
|---|---|
| Счётчик сувениров / «собрано N» | нет и не будет |
| Пустые слоты в коллекции как упрёк | нет: несобранного не существует, есть только собранное |
| «Ты не привёз сувенир» | запрещено формулировкой |
| Сувенир влияет на статус недели | нет: неделя закрывается событием |
| Публичность, сравнение с другими | нет |
| Отсчёт «осталось 2 дня привезти» | нет |
| Обязательность фото | нет: строка равноправна, «ничего не осталось» равноправно |

## Данные

Минимальные изменения схемы:

```prisma
model WeeklyStory {
  /// Ключ сувенира из каталога, зафиксированный при commit.
  /// Детерминирован по id истории — не меняется между сессиями.
  souvenirKey String?
}

model Memory {
  /// Что человек принёс. Пусто — валидный исход, а не пропуск.
  souvenirNote String?
  // фото сувенира — в существующий media[]
}
```

Каталог — константа `lib/souvenirs.ts` (`Record<LifeCategory, string[]>`), тексты — в
`messages/*.json`, как пробы онбординга. В `experiences.translations` не идёт: сувенир
привязан к категории, а не к конкретному впечатлению из каталога.

## Аналитика

Метрики — по принципу «оптимизируем completion, не screen time» (11-analytics-and-kpis):

- `onboarding_step_completed` с ключом строки бланка — где именно отваливаются.
- `onboarding_completed` + доля пропущенных строк: сколько бланков доходят пустыми.
- `souvenir_captured` — доля погашений со следом. **Это метрика вовлечённости, не
  цель.** Если она растёт, а `story_completed` стоит — механика превращается в задание
  и её надо убирать.
- Guardrail: доля погашений вообще (со следом и без) не должна упасть после релиза. Если
  упала — вопрос «что осталось?» читается как обязанность и мешает закрывать неделю.

## Открытые вопросы

1. **Что делает Ryk с сувениром дальше?** Молчит и хранит — или через месяц может
   вспомнить: «камень с Дуная всё ещё у тебя?». Второе сильнее, но легко скатывается в
   навязчивость.
2. **Год из корешков.** `YearSummary` сейчас показывает полосы по категориям. Стопка
   корешков за год — вероятно, лучший объект для «Было», но это отдельная задача.
3. **Сувенир и приглашённый друг.** Если шли вдвоём — след один на двоих или у каждого
   свой? Влияет на модель `WeeklyStory ↔ Memory` (сейчас 1:1).
